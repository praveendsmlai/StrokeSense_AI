## PHASE 4B.1 — Dashboard & Reporting Foundation

Work in the existing PeopleConnect backend. Continue from the completed Phase 3A, Phase 3C and Phase 4A audit.

**Objective:** Implement and verify Dashboard and Reporting functionality against FR-24, FR-25 and FR-26 using isolated synthetic Arun lifecycle data and existing Module 3 tables.

### 1. Mandatory constraints

- Use the existing FastAPI application, database models, services, routes and security architecture.
- **Windows environment: use `py -m` commands. Never use `python`, `python3`, Unix paths or Bash-specific commands.** If the active virtual environment requires its own interpreter, use the existing Windows `venv\Scripts\python.exe` path.
- Do not implement Arun's actual lifecycle APIs.
- Do not remove Praveen's existing lifecycle code, Connect model or foreign keys.
- Do not modify the frontend.
- Do not alter production/shared databases or run migrations against them.
- Use isolated temporary SQLite test databases with synthetic Arun schema/data.
- Reuse existing lifecycle adapters, canonical ID mapping, RBAC and test fixtures.
- Do not weaken authorization or replace HTTP tests with service-only tests.
- Do not delete existing tests merely to obtain a passing suite.
- Do not make unrelated changes.

### 2. Synthetic Arun test data

First inspect the existing isolated Arun test fixtures and reuse them wherever possible.

Prepare a deterministic test dataset containing:

- At least 5 canonical Connects across scheduled, completed and other relevant statuses.
- At least 12 participant records across 3 IBUs.
- Repeated employee participation to verify unique reach and touchpoint counts.
- At least 8 associated Module 3 actions covering open, in-progress, completed and overdue cases.
- Different Connect types, dates, locations and employee dimensions.
- BHR, BHR_LEADER and PLATFORM_ADMIN users with realistic authorized scopes.

Preserve the existing canonical-to-local Connect mapping. Ensure every action is associated with the correct mapped Connect.

### 3. FR-24 — Dashboard and Reporting filters

Inspect the actual requirements and Phase 4A audit before changing code.

Verify and implement any genuinely missing functionality for:

- Custom start/end dates.
- Supported date presets, including current month and previous quarter, as applicable to the requirements.
- Connect type, IBU, location, facilitator, theme and action status.
- Authorized employee reporting dimensions, including IBG, IBU, country, band, role and tenure.
- Reporting dimension allowlist validation.
- BHR/BHR_LEADER organizational scope enforcement.

Unauthorized requests must not expose out-of-scope data. Unknown or unsupported dimensions must be rejected with appropriate HTTP validation errors.

Preserve the existing Dashboard API contracts wherever possible.

### 4. FR-25 — Touchpoints, unique reach and percentages

Verify calculations against controlled test data:

- Total Connects and touchpoints.
- Unique employees reached using the correct employee identifier.
- Repeated touchpoints without double-counting unique employees.
- Breakdown by authorized dimensions.
- Correct application of date filters.
- Correct handling of empty datasets.
- Percentage calculations only when a valid, period-aligned denominator exists.

Where no valid denominator is available, return `null` rather than inventing a percentage or treating missing data as zero.

Use the actual FR-25 requirement definitions as the source of truth. Do not invent additional business rules.

### 5. FR-26 — Action analytics

Verify the required action analytics using the existing action tables and due-date history:

- Counts by action status.
- Open, completed and overdue actions.
- Due today and due soon.
- Aging buckets.
- SLA adherence and completion percentages.
- Extended due dates and applicable due-date history.
- Correct association with canonical Connects.
- No double-counting from legacy/canonical mapping.
- Date-filtered and scope-filtered calculations.

Follow the exact FR-26 calculation and denominator rules from the requirements.

### 6. Canonical versus legacy data isolation

Inspect both existing Dashboard execution paths.

- Canonical mode must use Arun lifecycle records as the authoritative Connect source.
- Local Module 3 records must supply associated downstream data through the verified mapping.
- Legacy mode must preserve existing behavior.
- Avoid duplicate aggregation.
- Never silently switch from canonical mode to legacy data if canonical access is unavailable.
- Do not remove the legacy path yet.

### 7. Tests and verification

Create focused tests for Dashboard/Reporting covering:

1. Canonical Connect counts.
2. Total touchpoints versus unique reach.
3. Duplicate participant handling.
4. FR-24 date and dimension filters.
5. Date presets.
6. FR-25 valid/invalid denominator cases.
7. FR-26 action status, SLA and aging calculations.
8. BHR in-scope and out-of-scope access.
9. BHR_LEADER scope enforcement.
10. PLATFORM_ADMIN authorized access.
11. Canonical versus legacy isolation.
12. Empty datasets and invalid requests.

Include genuine HTTP tests using the real FastAPI application and security dependencies, alongside service-level calculation tests.

Use test-only dependency injection where needed. Do not introduce test-only bypasses into production routes.

Run focused tests and the existing backend regression suite using Windows-compatible commands.

Provide:

- Files created or modified.

- Actual test execution commands.
- Exact passed, failed, skipped and error counts.
- Remaining limitations, if any.
- Confirmation that existing lifecycle, Arun integration boundary, frontend, production data and migrations were not changed.

Prioritize working code and verified tests over generating lengthy documentation. Never claim completion if tests remain failing.
